# 本地每分钟检查，有变化才发布

电脑保持开机联网，本地每 60 秒同步公开原表，同时通过公开接口 `https://yysrank.com/api/dyjc/get` 检查 [对弈竞猜实时风向](https://yysrank.com/dyjc.html)，比较场次、判断、赛果、风向及预测留档差异；有实际变化才提交并推送 `main`，由现有 GitHub Actions 发布到 Pages。只有 `fetchedAt` 改变时不提交、不发布，不需要云服务器。

## 启动

先确保本次网页代码已按正常流程发布一次，并能在当前电脑向仓库推送。服务读取当前仓库 `origin`，使用专用 `.local-publisher/` Git 副本，不把开发目录中的代码修改混入数据提交。

```bash
npm ci
npx playwright install chromium
npm run publish:watch
```

首次立即检查，此后每分钟检查，未结束的任务不会重叠。按 `Ctrl+C` 停止。仅检查一次可执行 `npm run publish:watch -- --once`。

`PUBLISH_WORKDIR` 可指定专用副本目录，`PUBLISH_BRANCH` 默认 `main`；`PUBLISH_INTERVAL_MINUTES` 默认 `1`。副本不能与当前开发目录相同，锁文件防止重复启动。

## 查看运行日志

控制台和仓库根目录 `.local-publisher.log` 同时记录带北京时间的日志，文件追加写入，重启后保留。查看最近记录或持续跟踪：

```bash
tail -n 50 .local-publisher.log
tail -f .local-publisher.log
```

日志包含启动 PID、每轮开始、拉取远端、原表和风向各自的抓取结果及真实抓取时间、推送或跳过原因、耗时、失败阶段及退出码；正在执行的轮次不会重叠，停止时记录退出和锁释放。推送成功只表示 Git 推送完成，Pages 是否上线仍需查看 Actions。失败日志不保存子进程原始输出，以免记录认证或访客信息。

可用 `PUBLISH_LOG_FILE` 指定日志文件（相对路径按启动目录解析），默认文件已忽略，不提交。日志持续追加，长期运行可停机后归档。修改脚本后需重启进程才能生效。


每轮无论数据是否变化，都会只读检查当前提交对应的 Pages 工作流，并核对线上快照内容（忽略抓取时间，包含预测留档）。日志区分数据推送、发布排队/执行中、部署失败、快照尚未更新、已核验上线及查询失败；推送不代表上线。`--once` 遇到部署失败或无法查询时返回非零退出码。

修复失败原因后，可在 Actions 点击 **Re-run all jobs** 重跑已有提交；或安装并登录 GitHub CLI 后执行 `npm run publish:watch -- --once --retry-deploy`。此参数仅重跑已确认失败的当前提交流程，不制造数据提交，每个失败流程在同一进程中最多重试一次，避免对确定性测试错误反复重跑。认证由 `gh` 管理，脚本不读取或保存凭据。

## 发布行为

- 拉取远端更新后同步数据，只有两个数据文件参与自动提交。
- 比较数据时忽略抓取时间，JSON 属性顺序变化也不触发发布。
- 首次预测记录与新赛果属于实际变化，会保留并发布；推送失败后下轮重试，不覆盖已有预测方向。
- Git 合并冲突或认证失败时保留线上旧版本，日志提示失败；修复发布副本或推送权限后再运行。
- Pages 有构建、发布及缓存延迟，一分钟是检查频率，不承诺变更恰好一分钟内上线。查看 Actions 确认发布完成。

网页每分钟检查已发布快照。没有新数据时，线上同步时间仍是最近一次发布的真实抓取时间，不会人为每分钟改成当前时间。

使用此方案时，仓库变量 `DATA_API_URL` 应保持未设置，让网页读取 Pages 自身的 `data-snapshot.json`。如已连接独立数据服务，可继续使用该服务；两种方案选其一即可。
